# perception_storage 检测算法 ROS2 迁移计划

## 1. 目标

在 `src` 下新建独立 ROS2 功能包 `perception_storage_ros2`，迁移现有
`perception_storage` 中以 `PerceptionStorage::running()` 为中心的完整检测链路。

迁移后的节点应满足：

- 支持 `lidar` 和 `tof` 两种传感器模式。
- 支持运行时选择左侧或右侧传感器。
- 保留 ROS2 YAML 参数加载。
- 使用 ROS2 标准消息控制检测的启动、切换和停止，不依赖自定义服务。
- 保持现有检测主流程及算法计算顺序不变。
- 保留代码中现有类名、函数名、成员变量名和局部变量名。
- 保留用于算法调试的中间结果和最终结果话题。
- 不依赖 `hecbot_msgs`、`hecbot_srvs`、导航、事件上报、monitor 或 pose tracker。
- 原 ROS1 包保持不变，便于迁移期间对照。

## 2. 范围边界

### 2.1 保留内容

- 点云、深度图及 CameraInfo 的订阅。
- 左右传感器选择。
- LiDAR 多帧缓存和融合。
- ToF 点云与深度图近似时间同步。
- `parse_frame()` 数据批处理逻辑。
- `couple_lidar()`、`couple_tof()` 预处理逻辑。
- `lidar_detector::inference()` 和 `tof_detector::inference()`。
- `post_process()` 及最佳目标选择逻辑。
- PCL、OpenCV、Eigen 和 Ceres 算法。
- 调试点云、图像、候选位姿、有效位姿和最终位姿发布。

### 2.2 删除内容

- `hecbot_msgs` 和 `hecbot_srvs` 依赖。
- `JString` 启停服务。
- `/hecbot_event_tracer/report_event` 客户端。
- tracker 状态订阅及事件发布。
- `tracker_cbk()`、`send_event()` 和外部业务 JSON 解析。
- `analyzer`、PCD/JPG 落盘和任务统计逻辑。
- `monitor` 可执行程序及其源码。
- `pose_tracker`、`nano_gicp` 及相关发布订阅。
- 导航侧全局参数读取。
- `repub_node.cpp`。
- ROS1 `tf` 和在线 TF 查询。
- 与核心检测链路无关的 ROS1 依赖和头文件。

## 4. ROS2 外部接口

### 4.1 检测控制

使用 `std_msgs/msg/String` 作为控制消息，不创建自定义消息或服务。

建议话题：

```text
/perception_storage/control
```

支持的 `data` 值：

| 值 | 行为 |
|---|---|
| `start_left` | 清空缓存并使用左侧传感器开始检测 |
| `start_right` | 清空缓存并使用右侧传感器开始检测 |
| `stop` | 停止检测并清空待处理缓存 |

非法命令只输出 warning，不改变当前状态。

同时增加以下启动参数，便于无需控制发布器时直接调试：

- `SettingPara/auto_start`：节点启动后是否自动开始。
- `SettingPara/sensor_side`：自动启动时选择 `left` 或 `right`。

状态切换继续沿用现有 `SLEEPY/LEFT/RIGHT` 语义，但移除业务请求信息
`ReqInfo` 和外部 JSON。

### 4.2 输入话题

LiDAR 模式：

- 左侧 `sensor_msgs/msg/PointCloud2`
- 右侧 `sensor_msgs/msg/PointCloud2`

ToF 模式：

- 左、右 `sensor_msgs/msg/PointCloud2`
- 左、右 `sensor_msgs/msg/Image`
- 左、右 `sensor_msgs/msg/CameraInfo`

所有输入话题名称通过参数配置，不在代码中固定。

传感器数据订阅使用 `rclcpp::SensorDataQoS()`；ToF 的点云和图像使用
ROS2 `message_filters::Synchronizer<ApproximateTime>`，两个输入采用一致 QoS。

### 4.3 调试输出

保留现有算法调试价值较高的输出：

- 最终检测位姿 `geometry_msgs/msg/PoseStamped`
- ROI `visualization_msgs/msg/MarkerArray`
- 预处理点云 `sensor_msgs/msg/PointCloud2`
- 检测深度图 `sensor_msgs/msg/Image`
- 候选点云和候选位姿
- 有效目标点云和有效目标位姿
- 本次运行累计位姿
- 原始输入转发点云/图像
- LiDAR 底部观测点云

发布前的“是否存在订阅者”优化继续保留，ROS2 中改用
`publisher->get_subscription_count()`。

## 5. 参数迁移

### 5.1 参数原则

- 原有参数分组、键名、含义和默认值尽可能保持不变。
- 改为 ROS2 参数声明和读取方式。
- 节点启动时完成参数校验；缺失或非法参数给出明确错误并退出。
- YAML 只在最外层增加 ROS2 必需的节点名和 `ros__parameters`。
- 代码通过 ROS2 点分参数名访问原有层级，例如原
  `LidarSensors/points_left` 对应 `LidarSensors.points_left`，不主动改成新的命名风格。
- 仅新增控制所必需的 `SettingPara/auto_start`、`SettingPara/sensor_side` 和
  `PubInfo/control_name`。

### 5.2 参数分组

```yaml
perception_storage_node:

      points_left: /livox/lidar_rear
      points_right: /livox/lidar_front

    TofSensors:
      points_left: /itof/itof_left_front/tof_frame/pointcloud

      image_left: /itof/itof_left_front/tof_frame/depthz
      image_right: /itof/itof_right_front/tof_frame/depthz
      camera_left: /itof/itof_left_front/caminfo
      camera_right: /itof/itof_right_front/caminfo
      width: 224.0
      height: 109.0
      flip: true
      range_compenstion: 0.0

    TargetInfo:
      upper_layer:

        length: 1.07
        width: 0.594

        feature: tag
        paras: [0.21, 0.20]

    SettingPara:
      sensor_type: lidar
      batch_size: [1, 20]
      auto_start: true
      sensor_side: right

    PubInfo:
      control_name: /perception_storage/control
      result_name: /hecbot_perception/storage_result
      naive_region_name: /hecbot_perception/storage/naive_region
      raw_name: /hecbot_perception/storage/base_points
      depth_name: /hecbot_perception/storage/depth_detect

      hyp_pose_name: /hecbot_perception/storage/proposal_pose

      evidence_pose_name: /hecbot_perception/storage/evidence_pose
      remember_pose_name: /perception/debug/poses
      repub_points_name: /perception/source/points
      repub_image_name: /perception/source/image
      lidar_capture_name: /perception/capture/points
```

原配置中的 `trouble_shoting`、`reference_pose`、`service_name`、`reference_name`
和 `refer_region_name` 虽然只服务于已删除的 analyzer 或外部流程，新配置仍保留
这些键以便直接复用原参数文件；运行时只加载但不会执行相应外部逻辑。
其余核心参数和输出话题名保持原样，包括原配置中已有的
`range_compenstion` 拼写，避免无意义的兼容性改名。

核心预处理和 inference 不依赖 `base_link` TF；删除 analyzer 后也不再需要
`matrix_base * target_pose` 统计。因此本包不创建 TF listener，不增加新的外参参数，
算法发布结果的 `header.frame_id` 继续继承输入数据。

## 6. 主检测流程迁移原则

迁移后保持以下顺序不变：

```text
传感器回调
  → 根据 active side 过滤
  → insert_buffer()
  → 后台 running() 循环
  → parse_frame()
  → couple_data()
      ├── couple_lidar()
      └── couple_tof()
  → detect_machine->inference()
  → post_process()
  → publish_msgs()
```

算法中的裁剪范围、滤波阈值、聚类阈值、候选生成、置信度计算、最佳目标选择和
批处理窗口行为均不主动修改。迁移期间只修改 ROS 类型、ROS API、资源路径和线程
退出机制。若发现算法缺陷，先记录，另行提交修复，避免与迁移改动混在一起。

## 7. ROS1 到 ROS2 的代码替换

### 7.1 节点和通信

- `ros::NodeHandle` → `rclcpp::Node`
- `ros::Publisher` → `rclcpp::Publisher<T>::SharedPtr`
- `ros::Subscriber` → `rclcpp::Subscription<T>::SharedPtr`
- `ROS_*` 日志 → `RCLCPP_*`
- ROS1 消息命名空间 → `pkg::msg::Type`
- ROS1 `ConstPtr` → ROS2 `ConstSharedPtr`
- `getNumSubscribers()` → `get_subscription_count()`
- `pcl::fromROSMsg()`、`pcl::toROSMsg()` 继续通过 `pcl_conversions` 使用
- `cv_bridge` 改用 ROS2 对应 API

### 7.2 参数与变量命名

- 构造函数中先 `declare_parameter()`。
- 读取并校验所有必需参数。
- `SettingPara.sensor_type`、`SettingPara.sensor_side` 限制为约定枚举值。
- `SettingPara.batch_size` 中实际选用的批大小必须大于零。
- 目标尺寸和补偿参数必须满足合理范围。
- 现有类名、函数名、成员变量名和局部变量名保持不变。
- 不做 `snake_case`、语义优化或拼写修正等重命名。
- 只有 ROS2 消息类型、publisher/subscriber 类型和 ROS API 强制要求的类型写法发生变化。
- 删除模块专用且已无引用的变量可以删除，但不重命名保留下来的变量。

### 7.3 线程和状态

- 保留独立 `running()` 工作线程，以尽量保持现有执行模型。
- `ros::ok()` 改为 `rclcpp::ok()` 与节点内部原子停止标志组合。
- 析构时先置停止标志，再可靠 `join()`。
- 禁止 `detach()`。
- 控制回调、传感器回调和处理线程共享的状态继续由 mutex 保护。
- `start_left/start_right/stop` 切换时原子地清空 `msg_packet` 和
  `process_queue`，避免左右数据混入同一批次。

## 9. 实施阶段

### 阶段一：建立新包骨架

- 新建 `perception_storage_ros2`。
- 编写 `package.xml` 和 `CMakeLists.txt`。
- 建立库目标和节点目标。
- 复制核心算法文件，暂不修改原 ROS1 包。

验收：`colcon list` 能识别新包，纯算法库进入编译阶段。

### 阶段二：清理业务和外部依赖

- 删除服务、事件、tracker、monitor 代码。
- 删除 TF 查询和 ROS1 package path。
- 清理未使用头文件和依赖。
- 用控制话题和本地参数替代外部启动流程。

验收：源码中不再引用 `hecbot_*`、`ros::`、TF1、monitor 或 pose tracker。

### 阶段三：迁移 ROS2 节点层

- 迁移参数、publisher、subscriber、消息类型和日志。
- 完成 LiDAR 左右订阅。
- 完成 ToF 左右点云、图像及 CameraInfo 同步。
- 实现控制话题及自动启动。

验收：节点能以 LiDAR/ToF 两种配置启动，控制命令能正确切换状态。

### 阶段四：迁移主检测链路

- 保持 `running()` 调用顺序。
- 迁移 PCL/ROS 消息转换。
- 迁移中间结果和最终结果发布。

验收：输入达到 batch size 后可以完成一次预处理、inference 和后处理。

### 阶段五：编译与静态检查

- 使用 Humble 环境执行指定包构建。
- 修复 `-Wall -Wextra -Wpedantic` 下与迁移相关的问题。
- 检查依赖声明与实际 include 一致。

验收：干净工作区中可以独立构建，不依赖另外三个 ROS1 包。

### 阶段六：回放和回归验证

- 使用相同输入 bag 分别运行 ROS1 原节点和 ROS2 新节点。
- 对比预处理点数、候选数量、有效目标数量和最终位姿。
- 对比预处理耗时和 inference 耗时。
- 分别验证 LiDAR left/right 和 ToF left/right。

验收：在允许的浮点误差范围内，关键算法输出与 ROS1 基线一致。

## 10. 测试清单

### 10.1 启动和参数

- 缺少 YAML 时给出明确错误。
- `SettingPara.sensor_type` 非法时拒绝启动。
- `SettingPara.sensor_side` 非法时拒绝自动启动。
- batch size 为零或负数时拒绝启动。

### 10.2 控制状态

- `start_left` 后只接受左侧数据。
- `start_right` 后只接受右侧数据。
- 左右切换会清空旧缓存。
- `stop` 后不再触发 inference。
- 重复 start/stop 不崩溃、不死锁。

### 10.3 LiDAR

- 左右 PointCloud2 均能转换为 PCL。
- 多帧累计数量与原逻辑一致。
- `couple_lidar()` 输出深度图、点云及映射表有效。
- 中间和最终调试话题可在 RViz2 中显示。

### 10.4 ToF

- CameraInfo 正确初始化一次并持续可用。
- 点云和深度图能够按近似时间同步。
- QoS 与传感器或 bag 发布端兼容。
- `couple_tof()` 输出尺寸及点云映射与原逻辑一致。

### 10.5 稳定性

- 无输入时 CPU 占用合理。
- 反复切换左右侧不会混用缓存。
- Ctrl-C 后工作线程可正常退出。
- 连续运行时缓存不会无界增长。

## 11. 主要风险与处理

| 风险 | 影响 | 处理方式 |
|---|---|---|
| ROS2 QoS 与传感器不匹配 | 节点启动但收不到数据 | 默认 SensorDataQoS，并通过 `ros2 topic info -v` 核对 |
| ToF 点云和图像时间戳差异 | 同步回调不触发 | 保留 ApproximateTime，并把队列长度参数化 |
| ROS1 与 ROS2 PCL 转换存在细微差异 | 点数或结果有变化 | 使用同一 bag 做逐阶段数据对比 |
| 控制切换与处理线程并发 | 混入旧侧数据或崩溃 | 状态切换和队列清理使用同一 mutex |
| 原代码缺少自动化测试 | 难判断行为是否保持 | 建立 ROS1 输出基线并保存关键统计 |

## 12. 完成标准

满足以下条件后视为迁移完成：

- 新包能在 ROS2 Humble 下通过 `colcon build`。
- 新包不依赖 `hecbot_msgs`、`hecbot_srvs` 和原 `perception_storage`。
- 不构建 monitor、pose tracker、nano GICP 或外部服务逻辑。
- LiDAR 和 ToF 模式都能通过参数选择。
- left/right 能通过标准 String 控制消息切换。
- `running()` 主检测顺序和核心算法保持一致。
- 调试话题输出可用。
- 节点可以正常启动、停止和退出。
- 至少完成一组 LiDAR 和一组 ToF 数据的回放验证。
